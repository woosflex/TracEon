# Correctness audit — 2026-09-20

Initial verdict (before the fixes below): the audited working tree was not fully correct. Normal-path tests pass,
but targeted probes expose process termination, silent parsing loss, and
large-input errors. No production code was changed during the initial audit. The subsequent authorized fixes are recorded below.

## Fixes applied — 2026-09-21

All twelve numbered findings have implementation fixes and regression coverage:

| Finding | Resolution | Regression evidence |
|---|---|---|
| 1 | Shared exception-safe worker launcher joins on launch failure and rethrows worker exceptions | Worker exception test; injected second pthread_create failure in FASTA, FASTQ, and parallel GZIP |
| 2 | FASTQ partitions follow the validated four-line cycle | All 40,000 ambiguous records and payloads checked in both index modes |
| 3 | Save sink splits complete fields into bounded 1 MiB chunks | 32 MiB sequence round-trip; individual C++ allocations must remain below 2 MiB |
| 4 | CAS reserves budget before allocation, including old/new buffer overlap | Concurrent admission and overflow checks |
| 5 | K-mer length guard compares size_t values | Valid 2 GiB mapped view encodes its first base |
| 6 | Server reaps completed workers; complete start/stop operations serialize | Connection churn, stop/restart tests, and Linux retained-stack growth check |
| 7 | Benchmarks and validation use private temporary workspaces | Pre-existing indexes, scratch directories, and cache files survive |
| 8 | Subprocess errors and lookup misses propagate | Failed-command and missing-record checks |
| 9 | Workers complete warmup before release; aggregate throughput uses shared elapsed time | Remote result checked against 17 requests / measured wall time |
| 10 | All numeric arguments and every thread-list item are validated | Zero, negative, malformed, and trailing-comma argument checks |
| 11 | CI creates exactly 150 sequence and quality bytes | Actual CI generator produces a loadable 36,000-record seed |
| 12 | K-mer fuzzer inserts before freezing, then checks collision/hit/pointer behavior | Instrumented k-mer API fuzz smoke run |

Additional fixes: both text index modes and both loader entry points are fuzzed;
text fuzzers compare accepted records against an independent line-based oracle;
fuzz inputs reuse bounded scratch files; binary fuzzing verifies restored
round-trips; remote tests are included in TSan CI. Save checks explicit close
errors. Parser validation rejects an empty CR-delimited identifier, and CRLF
handling preserves carriage-return payload bytes. SIMD bounds checks avoid
forming pointers beyond the valid range.

The corrected Release build passes all 12 registered CTest entries. All six
fuzz targets passed bounded ASan/UBSan/LeakSanitizer smoke runs (10,000 executions
per target), using temporary corpus copies. Focused ThreadSanitizer runs also
passed: remote tests (271 assertions) and worker/budget regressions (6 assertions).
These are bounded checks, not an
exhaustive correctness proof or a fresh cross-platform certification.

Still outside these fixes: crash-atomic cache replacement, authenticated remote
transport, and publication-grade cross-tool performance validation. These are
existing documented limitations, not claims made by the corrected benchmarks.

## Scope and evidence

Reviewed first-party runtime sources and public headers: Cache, SmartStrategy,
FASTA/FASTQ parsing, GZIP paths, v4/v5 serialization, lifecycle/publication,
remote client/server/protocol, k-mer encoding/C API, hashing, SIMD, and CRC.
Also inspected CMake, CI, Docker, fuzz harnesses, tests, command-line tools,
and benchmark/validation scripts. Historical reports are not correctness proof.
Vendored dependency internals were not independently audited.

The existing Release build was rebuilt successfully. Nine CTest entries passed
inside the sandbox. The remote entry initially failed because socket operations
were denied; it passed when rerun with local socket access. Thus all ten
registered entries passed. This was not a fresh ASan/UBSan/TSan run, a sustained
fuzz campaign, or a Windows/ARM portability test.

Findings below distinguish executed reproductions from source-level evidence.
P1 means high priority (data loss/process failure); P2 means a significant
correctness, resource, or verification defect.

## Findings

### 1. P1 — Parallel loaders abort instead of propagating thread failures

Locations: `src/SmartStrategy.cpp:1163`, `:1275`, `:624`.

The thread-launch loops hold already-started `std::thread` objects in a vector.
If a later launch throws, unwinding destroys joinable threads and calls
`std::terminate`. Parser workers also allocate into maps without catching
exceptions, so a worker-side allocation failure terminates the process instead
of reaching the load path's cleanup handler.

Reproduced: loaded an 11 MiB FASTA while an LD_PRELOAD shim made the second
`pthread_create` return EAGAIN. `traceon_driver` exited by SIGABRT (return -6),
printing `terminate called without an active exception`, rather than returning
its handled-error status. The same launch pattern exists in FASTQ and parallel
GZIP loading.

Fix: guarantee joining during unwinding (e.g. `std::jthread`) and transport
worker exceptions back to the calling thread after all workers have joined.

### 2. P1 — FASTQ boundary guessing silently changes the accepted record set

Location: `src/SmartStrategy.cpp:1215` (especially the line+2 '+' test).

The validator enforces framing and equal payload lengths, but imposes no
sequence-alphabet restriction. The parallel parser nevertheless assumes a
sequence never starts with '+'. With '@'-leading quality and '+'-leading
sequence, a quality line can pass its header test. Workers then parse from the
wrong phase, produce a bogus identifier, and discard real records.

Reproduced with unique `@rN` headers, 150 '+' sequence bytes, a '+' separator,
and 150 '@' quality bytes: ten records load as ten; 40,000 records load as
4,453 on this host, returning success. The exact loss depends on thread count.
These are structurally accepted payloads, not ordinary biological nucleotide
sequences; if the intended alphabet excludes them, the validator must reject
them instead of permitting size-dependent silent loss.

Fix: derive chunk starts from known four-line record boundaries, or enforce the
alphabet assumption consistently before parsing. Add a serial/parallel parity
check that verifies identifiers and payloads, not just successful loading.

### 3. P2 — Save memory is proportional to the largest record

Location: `src/SmartStrategy.cpp:1468`.

`serializePayload` supplies complete sequence fields. The save sink appends the
entire field before checking the 1 MiB flush threshold, then expands the LZ4
output buffer for that full input. The claimed bounded streaming buffers can
therefore become two chromosome-sized buffers, causing save-time memory failure
even when the loaded snapshot fits memory.

Reproduced: saving a single 32 MiB manual sequence performed an individual
33,622,024-byte allocation during save. The input buffer also receives the
complete 32 MiB field.

Fix: feed each supplied field through bounded slices, flushing before the
buffer exceeds STREAM_CHUNK_SIZE.

### 4. P2 — Parallel GZIP memory-budget admission is racy

Location: `src/SmartStrategy.cpp:540` through `:553`.

Workers load the aggregate reservation, check it, allocate, and only then
increment it. Two workers can both pass against the same old value and exceed
the shared cap. Example: a cap of 100, current reservation of 60, and two
concurrent growth requests of 30 both pass and produce a reservation of 120.
Atomic individual operations do not make this check-and-reserve atomic.

Source-level finding; no machine-exhaustion experiment was run.

Fix: reserve budget atomically with compare/exchange before allocating, and
release the reservation if allocation fails. Account separately for temporary
reallocation/merge memory if the cap is meant to bound actual peak memory.

### 5. P2 — K-mer encoding rejects valid large views

Location: `include/KmerEncoding.h:29`.

Casting `seq.size()` to int before comparing with k narrows a size_t. On this
64-bit build, a 2 GiB view becomes a negative int, so encoding even the first
valid base fails. The contract only requires the view to contain at least k
bytes; it does not impose an INT_MAX total length.

Reproduced using a valid anonymous 2 GiB mapping with the first byte 'A':
`encode_kmer(view, 1, out)` returned false. Only one page needed touching.

Fix: after validating k, compare `seq.size() < static_cast<size_t>(k)`.

### 6. P2 — Finished remote workers accumulate until server shutdown

Locations: `src/TraceonServer.cpp:176`, `:271`, `:300`.

Every accepted connection appends a joinable worker. A finished worker closes
its socket but is neither joined nor removed until stop(). Thus even strictly
sequential short connections cause monotonically growing thread bookkeeping
and retained joinable-thread resources. Docker's repeated TCP healthcheck
exercises precisely this path. This is distinct from the documented absence
of a simultaneous-connection admission limit.

Source-level finding. Fix: reap completed workers during service, preserving
the server object's lifetime and stop/join guarantees.

### 7. P1 — Benchmark cleanup can delete pre-existing user indexes

Location: `benchmarks/value_chain_benchmark.py:184`.

`cleanup()` scans both REAL_DATA_DIR and the current directory and removes every
file ending in `.fai`, `.gzi`, `.fxi`, or `.traceon_bench_tmp`, regardless of
whether this run created it. main() invokes cleanup in finally, including on
failure. Running the benchmark beside existing indexed data can destroy its
indexes. No destructive reproduction was run.

Fix: use a run-owned temporary directory and remove only artifacts created by
that run. Similar ownership care is needed for the fixed `.traceon` output
created and unconditionally unlinked by `validate_real_data.py:435` and `:486`.

### 8. P2 — Benchmark failures can become apparently valid timings

Location: `benchmarks/value_chain_benchmark.py:125`.

`run_timed` ignores the subprocess return code and normally discards stderr,
so a failed invocation still returns a positive timing to the comparison.
Its PyFastX lookup snippets also swallow all lookup exceptions. Missing keys
can consequently look like fast successful work. This matters when rerunning
the scripts even though README correctly withdraws current comparative claims.

Fix: require successful subprocess exit, verify expected hit counts and payload
hashes, and fail the run when equivalence cannot be established.

### 9. P2 — Concurrent benchmark throughput calculations are wrong

Locations: `benchmarks/remote_bench.cpp:136`,
`benchmarks/read_scaling.cpp:174`, `:244`.

Remote benchmark ops/s divides request count by the sum of overlapping request
latencies. That measures reciprocal mean latency, not aggregate throughput:
eight simultaneous 1 ms requests are reported as 1,000 ops/s rather than the
8,000 ops/s attained over the shared 1 ms interval.

Read-scaling releases its go flag without waiting for every worker to finish
warmup. Workers can begin timing at different moments, yet total operations
are divided by the largest individual duration. That duration need not equal
the combined wall-clock interval, overstating concurrency/scaling.

Source-level findings. Fix: synchronize worker readiness and measure aggregate
throughput over a coordinator-owned wall-clock interval; retain per-request
latencies as a separate statistic.

### 10. P2 — Benchmark argument validation permits a segmentation fault

Location: `benchmarks/read_scaling.cpp:284`.

`--reps=0` leaves result vectors empty, then dereferences min_element and front.
Reproduced with `--records=1 --keys=1 --count=1 --warmup=0 --threads=1 --reps=0`:
SIGSEGV (return -11). Only the first element of --threads is validated; later
zero/negative thread counts also reach invalid measurement/allocation paths.
`remote_bench` similarly lacks the local mode's empty-sample guard in remote
mode, allowing `--keys=0` to reach modulo-by-zero.

Fix: validate all counts and every thread-list entry before building data or
starting workers; reject empty sample sets in both remote/local modes.

### 11. P2 — CI's purported parallel FASTQ seed is malformed

Location: `.github/workflows/fuzz.yml:62`.

For seq_len=150, `"ACGT" * (seq_len // 4)` produces 148 sequence bytes, while
quality has 150. The new validator rejects the seed before the parallel parser.
Thus this generated seed no longer supplies the stated parallel FASTQ coverage.

Reproduced one generated record: load returns status 1 with `FASTQ sequence and
quality lengths differ`.

Fix: generate exactly seq_len bases and assert seed validity/record count before
starting fuzzing.

### 12. P2 — K-mer fuzzer never builds a nonempty index

Location: `fuzz/fuzz_kmer_api.cpp:40`.

The first operation is always get() on a newly created empty index. This freezes
it, making every subsequent insert fail. No input can exercise successful
insertion, collision handling, retrieval from a populated map, or pointer
stability through this harness.

Source-level finding. Fix: populate before the first lookup and derive the
operation schedule from input so successful build/read transitions are reachable.

## Additional verification gaps and known limitations

- FASTA and FASTQ fuzzers select NGS mode from the first byte's low bit. Valid
  FASTA starts with '>' (62), valid FASTQ with '@' (64): both always choose
  GENOME. Execute both modes or select mode independently of format magic.
- `fuzz_common.h` creates a new temporary file on every iteration without
  removing it. Long fuzz campaigns consume disk/inodes and may abort for a
  harness failure. Reuse a per-process input file or unlink after each case.
- Text fuzzers check memory safety but do not compare accepted results with an
  independent parser. Silent record loss can remain invisible to them.
- The TSan workflow runs core test executables but omits `test_remote`, leaving
  remote lifecycle concurrency outside that CI check.
- Cache writes truncate their target and are not crash-atomic, as already
  documented. saveBinary also relies on ofstream destruction for its final
  close; explicit close/error checking would make late write failures visible.
- Server stop/restart redesign is already deferred in README. In particular,
  running_ becomes false before joining completes, allowing an overlapping
  start() to reuse state while the old stop() still operates on descriptors.
  Do not treat overlapping restart as verified by sequential restart tests.
- Borrowed-view safety depends on the documented reader-quiescence contract;
  read-versus-reload concurrency was not treated as a supported use case.
- No new defect was established in ordinary v4/v5 checksum/length validation,
  full-identifier lookup, or the C API's synchronized freeze transition.
  Passing tests and source review do not constitute proof for all inputs.
