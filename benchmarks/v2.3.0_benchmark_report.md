# TracEon v2.3.0 Benchmark Report

**Run date:** 2026-09-06  
**Revision:** `e0275c9` (`v2.3.0`) plus documentation and benchmark-harness cleanup  
**Build:** Release, CMake 4.4.2, GCC 16.2.1, C++20  
**Host:** Intel Core Ultra 5 125H, 14 cores / 18 hardware threads, 18 MiB L3  
**OS:** Linux 7.1.9-arch1-2, x86-64, single NUMA node

## Scope

This run covers TracEon's quick cache lifecycle benchmark, lock-free read
scaling, and loopback remote-read latency. Results are local measurements, not
cross-tool comparisons. CPU placement and frequency were left to the operating
system, so small run-to-run variation is expected.

## Verification

The Release build completed successfully. All ten TracEon CTest targets passed,
including the combined core suite, six split domain suites, remote integration,
k-mer tests, and the C linkage test. The first sandboxed run could not open
loopback sockets; rerunning with local socket permission passed all targets.

## Quick lifecycle benchmark

Command:

```sh
python3 benchmarks/quick_benchmark.py
```

The harness uses deterministic synthetic data (`seed=42`) and measures process
wall time for load, v4 save, and restore. Compressed-input ratios compare the
compressed source file with the v4 cache and therefore can be below 1×.

| Scenario | Source size | Load | Save v4 | Restore v4 | Cache size | Source/cache ratio |
|---|---:|---:|---:|---:|---:|---:|
| WGS 10 MB | 8.9 MB | 0.017 s | 0.045 s | 0.024 s | 2.6 MB | 3.4× |
| WGS GZIP 10 MB | 1.5 MB | 0.043 s | 0.075 s | 0.016 s | 2.6 MB | 0.6× |
| Reference 10 MB | 9.5 MB | 0.014 s | 0.074 s | 0.026 s | 5.4 MB | 1.8× |
| Reference GZIP 10 MB | 2.7 MB | 0.076 s | 0.111 s | 0.014 s | 5.4 MB | 0.5× |
| WGS 100 MB | 89.3 MB | 0.112 s | 7.788 s | 0.098 s | 19.6 MB | 4.6× |
| WGS GZIP 100 MB | 14.8 MB | 0.482 s | 7.710 s | 0.172 s | 19.6 MB | 0.8× |
| Reference 100 MB | 99.2 MB | 0.182 s | 32.369 s | 0.146 s | 38.9 MB | 2.5× |
| Reference GZIP 100 MB | 28.3 MB | 0.678 s | 29.811 s | 0.141 s | 38.9 MB | 0.7× |

The smart LZ4_HC save path trades one-time cache creation cost for fast repeat
restores. On the 100 MB cases, restore remained between 0.098 and 0.172 seconds.

## Lock-free read scaling

Command:

```sh
./build/read_scaling
```

Configuration: 100,000 records, 100,000 distinct keys, 20 passes per thread,
two warmup passes, three repetitions, seed 42. Every run reported 100% hits and
a stable checksum.

| Threads | Median ops/s | Minimum ops/s | Scaling | Median latency |
|---:|---:|---:|---:|---:|
| 1 | 10,325,628 | 7,794,964 | 1.00× | 0.097 µs/op |
| 2 | 19,433,220 | 16,567,291 | 1.88× | 0.103 µs/op |
| 4 | 52,464,280 | 44,857,518 | 5.08× | 0.074 µs/op |
| 8 | 75,143,269 | 64,244,940 | 7.28× | 0.099 µs/op |
| 14 | 99,215,411 | 81,244,482 | 9.61× | 0.128 µs/op |

The result confirms near-linear scaling through eight threads and a plateau on
the host's hybrid-core topology beyond that point. The 14-thread median is
99.2 million reads per second; it should not be generalized to other CPUs.

## Loopback remote reads

Fixture: the 3,000-record `docker/data/sample.fasta`, converted to a v4 cache.
Both local and remote measurements used 1,000 sampled keys, 20,000 measured
requests, 2,000 warmups, seed 42, and four remote client threads.

| Mode | Median | p95 | p99 | Throughput |
|---|---:|---:|---:|---:|
| Local | 0.07 µs | 0.09 µs | 0.10 µs | 13,298,783 ops/s |
| Loopback TCP | 21.45 µs | 43.89 µs | 53.08 µs | 40,300 ops/s |

The remote figure measures the complete request/response path, including TCP
framing and client-side CRC32C verification. It is not a substitute for a
cross-host network benchmark.

## Reproduction notes

- Configure with `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release`.
- Build with `cmake --build build -j4`.
- Run project tests from `build/`.
- Remote tests and benchmarks require permission to bind loopback sockets.
- The comprehensive cross-tool matrix was not run in this pass because its
  optional Python/tool dependencies were not installed; no comparative claims
  were refreshed from this run.
